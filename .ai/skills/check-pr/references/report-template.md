# Report templates

Two kinds of comments: **one inline comment per finding**, on its line in the PR diff, and **one short summary comment** on the PR. Each finding is explained next to its code so a Go beginner sees the context. The summary doesn't repeat what the inline comments say.

Only blocker and major findings are reported for now (minor and nit are ignored to keep the review short), and only when they can cause an error, a regression, or a breaking change. Style, naming, doc comments, and optional tests (nits) are never reported.

## 1. Inline comment (one per finding)

Post on the exact line (or line range) the finding is about.

### With a code suggestion (fix replaces the commented lines)

````markdown
**⚠️ major · Error is returned without context**

**What:** `os.MkdirAll` failed, but the error is returned as is.
**Why it matters:** The caller only sees "permission denied" with no hint that it happened while creating the log folder, so the bug is hard to trace. In Go you add context by wrapping the error. `%w` keeps the original inside, so `errors.Is` still works.
**Fix:**
```suggestion
	if err := os.MkdirAll(filepath.Dir(path), 0o750); err != nil {
		return nil, fmt.Errorf("logger: create log folder: %w", err)
	}
```
````

Rules for the `suggestion` block:
- It **replaces exactly the lines you commented on**. For a 3-line fix, comment on all 3 lines (start line → end line).
- Keep the file's indentation (tabs in Go). The result must compile and pass `make lint`.
- One suggestion per comment. If the fix needs an import or a change elsewhere, say so in **Fix** in one line ("also add `"fmt"` to the imports").

### Without a suggestion (fix is elsewhere, or is a new test)

````markdown
**⚠️ major · Missing test: transition from `completed`**

**What:** `Start()` has no test for a work order that is already `completed`.
**Why it matters:** If someone changes the status check, a finished job could be restarted and nobody would notice.
**Fix:** add this row to the table in `internal/domain/work_order_test.go`:
```go
{name: "from completed", status: StatusCompleted, wantErr: ErrInvalidTransition},
```
````

### Repeated problem

The first occurrence gets the full comment. Later ones stay short, but still include a suggestion when one fits:

````markdown
**⚠️ major · Same as `logger.go:73`**: error returned without context.
```suggestion
		return nil, fmt.Errorf("logger: open log file: %w", err)
```
````

### Severity labels

| Label | Use |
|---|---|
| `**⛔ blocker · …**` | Must fix before merge |
| `**⚠️ major · …**` | Should fix before merge |
There are no labels for minor findings or nits: they are not reported.

## 2. Summary comment (one per PR)

The first line must be the marker, so later runs update this comment instead of adding a new one. The second line is the verdict marker: the workflow reads it to set the **Claude Review** status (`ready` → success, `needs-changes` or `blocked` → failure) and compares `commit` with the PR head. Use the full 40-character SHA (`headRefOid`).

````markdown
<!-- check-pr -->
<!-- check-pr-verdict: <ready|needs-changes|blocked>; commit: <full 40-character sha> -->
## 🔍 PR check: <Ready ✅ | Needs changes ⚠️ | Blocked ⛔>

**Commit:** `<short sha>` · **Model:** <model> · **Gate:** Lint ✅ Test ✅

<One or two plain sentences: the overall picture and what to fix first.>

| Severity | Count |
|---|---|
| ⛔ blocker | <n> |
| ⚠️ major | <n> |

**Inline comments:** every finding is commented on its line; most have a suggestion you can apply with *Commit suggestion*. (At most 10 inline comments; any extra findings are listed here only.)
- ⛔ `internal/x.go:42`: <short title>
- ⚠️ `internal/y.go:10`: <short title>
- …

### Not on a diff line
<Findings about unchanged code, missing files, or the whole PR, in What / Why / Fix form. Or "None".>

### Test cases
List the primary cases of new or changed logic. Group the tested ones in one row.

| Function | Case | Status |
|---|---|---|
| `WorkOrder.Start` | happy path and invalid inputs | ✅ tested |
| | from `completed` → `ErrInvalidTransition` | ❌ missing (see inline comment) |
| | edge case that guards nothing risky | ❌ missing (table only, no comment) |

### Conventions
- Commits: ✅ / ❌ `<subject>`
- PR template: ✅ / ❌ <what's missing>
- OpenAPI: ✅ / ➖ no endpoint changes / ❌
- Migrations: ✅ Up + Down / ➖ none / ❌

<sub>Generated by the `check-pr` skill. Comment `@claude-code-review` to re-run.</sub>
````

## Writing rules

- One finding = one inline comment. Never merge several findings into one comment.
- Every blocker and major has **What / Why it matters / Fix**. Keep each one short and give a suggestion when a direct fix exists.
- Plain language for a beginner; explain each Go term the first time it appears.
- Suggestions must be correct: right indentation, compiles, passes lint. If you're not sure, use a plain ` ```go ` example instead.
- No invented findings, no minors, and no nits. If you are not sure something can cause an error or a regression, leave it out. Write "None" in sections with nothing to report.
- Never paste secrets; point to `file:line`.
